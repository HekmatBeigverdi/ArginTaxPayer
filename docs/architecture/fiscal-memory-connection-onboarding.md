# ArginTaxPayer — Fiscal Memory Connection & Key Onboarding Specification
Status: **Design proposal / owner requirements captured; NOT IMPLEMENTED**
Date: 2026-10-19
Applicable roadmap: Phase04 onboarding contract; Phase09 cryptography; Phase10 authoritative connection tests; Phase12 entitlement enforcement; Phase16 administration.
This document does not change the fixed numbering of Phase08 steps.

## 1. Terminology and critical safety distinction
- **Fiscal memory identifier** (شناسه یکتای حافظه مالیاتی): issued/obtained via taxpayer portal; never generated by ArginTaxPayer.
- **Asymmetric private key** (کلید خصوصی): long-lived RSA/other officially supported private key. A plaintext `private.txt` may contain PEM key material; it is **not** an API access JWT.
- **Public key**: derived from the same key pair and delivered to the user for portal registration, subject to published portal format.
- **CSR**: request for a certificate, not a private key, not a portal fiscal memory ID and not a JWT.
- **Access token/JWT**: short-lived token issued by tax-authority authentication exchange. Never advertise a generated RSA private key or CSR as “سامانه مودیان توکن”.
- **Connection type in product**: (A) `without-independent-certificate` / legacy key-based path (first implementation target **only if** supported by current official API/SDK) and (B) certificate-backed signature path (deferred). “Without signature” must NOT imply unsigned transport, unsigned requests, or bypassing authority requirements.

- Domain rule scope source: `RC_IITP.IS_V7.9` (Tir 1405) stored in `InvoicePatternMatrix`, defines invoice **data rules**, not the contemporary connection contract.
- `docs/roadmap/18-phases.md` expressly places generation/import/CSR in Phase09, authority authentication/read-only test in Phase10, plan/entitlement in Phase12. The current `FiscalMemoryManagementService` persists one pending memory's identifier only; it does not generate keys, securely ingest private keys or prove connectivity.
- Previous user-supplied official SDK files are mentioned in project history, but a matching current-project stored file could **not** be located in the accessible file index for this review. Therefore compatibility of the requested `without-independent-certificate` option with the **newest live authority protocol is not verified**. Do not implement an invented endpoint or promise success until the exact official SDK edition, credential and transport requirements are checked against the supplied files; record SHA256/version and precise document clauses on implementation.
- Community examples are non-authoritative and MUST NOT override the official SDK.

## 3. UI: two modes, priority legacy key-based
`Fiscal memory & taxpayer connection` on taxpayer details, visible according to scoped roles:
1. Mode selector: **روش مبتنی بر کلید (بدون گواهی امضای مستقل — در انتظار تأیید سازگاری SDK)** / **روش گواهی امضا (بعداً)**.
2. For the prioritized key-based mode, onboarding variant:
   **A. Create a new key pair**
     - Read scoped taxpayer profile and detect missing required attributes from the **selected official SDK flow** (person vs company, taxpayer national/economic IDs, postal/address and required CSR distinguished from directly generated keys).
     - Show field-specific missing-data checklist and deep links to edit customer/taxpayer profile; never invent profile fields or allow an incomplete flow to proceed.
     - Generate private/public material server-side with cryptographically secure primitives and an officially supported algorithm/key size. Keep key private in an encrypted envelope/vault, never browser/localStorage/logs/database plaintext. Do not echo the private key in API JSON or return it again after acknowledgement. Display/allow download of **public** artifact in exactly the supported portal format; CSR only if required by this supported workflow.
     - User registers public artifact in authority portal and obtains fiscal memory identifier, then enters it in software. Identifier is independently validated, tenant-scoped and unique per supported authority rules.
   **B. Import previously connected credentials**
     - User enters an existing fiscal memory identifier and uploads `private.txt` through bounded authenticated TLS-only endpoint. Parse PEM/PKCS#8 or explicitly supported formats; reject malformed/weak/encrypted-key formats until password workflow exists. Derive public key locally from private and compare against user-provided or officially retrievable registered public key (if available); do not silently assume matching registration.
     - Encrypt before persistence with KMS/vault and managed key rotation. Show fingerprint, never secret contents. Prevent cross-customer key disclosure and duplicate bindings.
3. Both variants end in **read-only connection test** once Phase10 connector exists. Distinguish `authenticated`, `registered key mismatch`, `invalid fiscal memory identifier`, `authority unavailable`, `timeout`, `not supported by edition`; do not show “connected” based only on local import, public key generation or a green ping.
4. Do not send any tax invoice as part of the connection test. No real provider call in developer tests without explicitly configured sandbox/test authorization.
5. All onboarding/exception actions are audit logged with actor, taxpayer, memory, action, UTC time, revision and **key fingerprint only**, never keys/JWT.

## 4. Plans, limits and exception workflow
- **Time-based/annual single-memory plan**: one active fiscal-memory binding per permitted subscription scope. At the first successful authority connection, bind the chosen memory to that subscription and retain binding history. Attempt to add or switch to a second identifier returns `SECOND_MEMORY_REQUIRES_APPROVAL`, even if another identifier was entered; never silently rebind.
- For subsequent memory: customer requests exception with new memory identifier, reason and evidence; owning Level2 may inspect/request under scoped permissions; **Level1 alone approves or denies** the exceptional binding, with reason, expected revision, expiry/plan implications and append-only audit. No approval means no additional key issuance/import/activation or connection test for extra memory. A previously approved one-time exception cannot be replayed.
- **Quantity plan**: model multiple memory bindings according to actual contract/entitlement policy, with cap, usage and expiration controlled by Phase12. No universal unlimited assumption; the exact permitted number is a business plan setting. Query scope still tenant-bound.
- Differentiate customer account, taxpayer and fiscal memory: a customer can own several taxpayers; the annual plan's one-memory rule applies to the subscribed binding scope, NOT automatically to all customers of Level2.
- Plan changes, cancellation, transfers and expired packages must never rewrite historical invoices, connected memory audit or already-applied fees. Exception approval is not a substitute for official authority permissions.
- Prioritize enforcement in **server transaction** using a lock/unique constraint + idempotency key + revision CAS. Frontend-only limits are insufficient.

## 5. Suggested domain records (Phase09/12 migration design only)
- `FiscalConnectionProfile`: customerId, taxpayerId, fiscalMemoryId, connectionMode, onboardingVariant, authorityEdition, status, lastVerifiedAt, lastErrorCode, revision; unique scoped identity.
- `ProtectedKeyMaterial`: secret vault handle (not bytes), public key SHA-256 fingerprint, key algorithm, rotation state, created/revoked UTC, authorized owner and audit ref; protect at rest/in transit.
- `FiscalMemorySubscriptionBinding`: planId, taxpayerId, fiscalMemoryId, effectiveFrom/To, immutable initially bound identity, exception approval reference; audited.
- `FiscalMemoryExceptionRequest`: requester, customer, taxpayer, proposed identifier, reason, state, approver Level1, revision, UTC timestamps, audit events.
- `FiscalConnectionTestResult`: status, diagnostic code, response metadata redacted, provider SDK version, timestamp, correlation id.
All constraints and migrations must be additive, safe on `argintaxpayer_test`, with a reviewed SQL preflight; **none is authorized for immediate execution by this document.**

## 6. Acceptance / negative tests
- Incomplete taxpayer fields produce precise warnings; no secret created for an incomplete profile.
- Generated public key and retained private key form a pair, and imported `private.txt` derives the expected public fingerprint; no key material in browser payloads, logs or exports.
- Another customer/Level2 cannot read or test a foreign memory; no actor can retrieve a stored private key after it is sealed.
- First annual binding succeeds; unapproved second binding/import/test denied even under concurrent requests; Level1 approval permits exactly the sanctioned exception.
- Connection check differentiates valid authentication and authority rejection/timeout; no accidental invoice submission.
- Historical memory assignment unchanged after subscription switch/customer transfer.
- Current official SDK compatibility and required signature/certificate behavior evidenced before any live connection functionality is declared complete.

## 7. Open authority questions (block live implementation)
1. Exact version/hash of user's latest official SDK and current official API specification; which operations legitimately work without an independent certificate?
2. Does new-key onboarding require an actual accredited certificate (versus bare RSA public key) for that version and account type?
3. Accepted key formats (PKCS#1/PKCS#8), RSA sizes, signature algorithms, nonce/JWT exchange and official read-only test endpoint for the selected edition.
4. Formal source for any tax-authority-side limit on fiscal memory IDs — do not conflate with our commercial plan limit.
5. Decide encrypted key custody deployment (KMS/HSM/secret store), operator backup/recovery and whether user export of freshly created private key is desired. Default is no re-export.

## 8. Delivery separation
- **Phase08 Step10**: display fiscal memory metadata and taxpayer profile validation hints only; no real key generation/import/connection test/plan payment enforcement, so Step10 does not become a stealth implementation of future phases.
- **Phase09**: secure key generation, public artifact / CSR where supported and legacy key import, fingerprint checks and audit.
- **Phase10**: real version-pinned authority JWT/authentication, read-only connection diagnosis (no invoice submission during check).
- **Phase12**: enforce active subscription limits and governed exception lifecycle, initially fail closed until supported plan contracts exist.
- **Phases16/17**: administrator requests UI, alerts, secrets protection, security testing and operational hardening.
