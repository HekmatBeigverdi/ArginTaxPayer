# پشتیبانی صورتحساب فروش نوع دوم

## هدف

کاربر بتواند صورتحساب فروش عمومی نوع ۲ (`inty=2`, `inp=1`) را ذخیره، بررسی و در صورت تأیید صریح به سازمان ارسال کند؛ مسیر واقعی ارسال باید در Sandbox و Production، با جداسازی کامل محیط‌ها، پشتیبانی شود. خطای فعلی بررسی برای نوع ۲ باید با اعتبارسنجی واقعی این نوع جایگزین شود.

## محدوده و محدودیت‌ها

- تغییر فقط برای نوع ۲، الگوی فروش ۱ و موضوع اصلی است. سایر الگوها و موضوع‌های زنجیره‌ای در این کار فعال نمی‌شوند.
- اطلاعات خریدار در نوع ۲ اختیاری است؛ در صورت نبود، فیلدهای وابسته به خریدار در JSON خروجی حذف می‌شوند، نه اینکه مقادیر نوع ۱ به آن نسبت داده شوند.
- قواعد پرداخت/تسویه، فروشنده، شناسه مالیاتی، کالا/خدمت، واحد، VAT، تاریخ اثر قواعد و ساختار امضا باید با سند رسمی جاری و نمونهٔ معتبر تأیید شوند.
- آزمون خودکار، build و fixtureها هیچ ارسال زنده‌ای انجام نمی‌دهند. ارسال عملیاتی فقط با اقدام صریح کاربر برای همان فاکتور و محیط انجام می‌شود.
- فعال‌سازی سرویس، مهاجرت پایگاه داده و تغییر secret/کلید خارج از پیاده‌سازی این تغییرند و گیت‌های عملیاتی خودشان را دارند.
- Sandbox و Production باید با credential، URL، حافظه، serialization، signature، idempotency و reconciliation مستقل پوشش داده شوند؛ هیچ fallback بین دو محیط مجاز نیست.
- rollout به‌صورت مرحله‌ای است: ابتدا یک ارسال واقعی Sandbox با تأیید صریح و تطبیق رسید/استعلام، سپس ارسال Production برای فاکتور مشخص با تأیید صریح مستقل. آزمون Sandbox موفق به‌تنهایی مجوز ارسال Production نیست.

## رویکردهای بررسی‌شده

1. حذف شرط نوع ۱ از پیش‌بررسی: رد شد؛ خطای UI را پنهان می‌کند ولی snapshot و payload نوع ۲ را معتبر نمی‌سازد.
2. پشتیبانی سرتاسری و fail-closed نوع ۲: انتخاب شد؛ قواعد، snapshot، projection، payload، امضا و آزمون‌های هر مرز صریحاً نوع ۲ را می‌شناسند و اطلاعات نامعتبر را رد می‌کنند.
3. تبدیل فاکتور به نوع ۱: رد شد؛ انتخاب قانونی نوع صورتحساب را عوض می‌کند و اطلاعات خریدار/اعتبار مالیاتی متفاوتی دارد.

## تصمیم‌های اجرایی

- ابتدا پیام خطای واقعی ثبت‌شده در UI و پاسخ API مشخص می‌شود؛ یافتهٔ فعلی `invoice.snapshot.pattern.unsupported` برای نوع غیر ۱ به‌تنهایی علت قابل‌مشاهدهٔ بخش بررسی است.
- پیش از هر تغییر قواعد، نسخه و تاریخ‌اثر سند رسمی، جدول کامل فیلدهای نوع ۲ و نمونه JSON باید از مرجع رسمی بررسی و در ماتریس پروژه ثبت شوند. کپی‌های ثانویهٔ وب جایگزین این مدرک نیستند.
- اعتبارسنجی نوع ۲ سیاست خودش را دارد؛ از قواعد buyer و settlement نوع ۱ به‌صورت ضمنی ارث نمی‌برد.
- projector نوع ۲ خروجی مستقل و نسخه‌دار تولید می‌کند و در آزمون‌های طلایی، فیلدهای الزامی و حذف/اختیاری‌بودن فیلدهای خریدار با مرجع تطبیق داده می‌شوند.
- تست‌های منفی برای نوع/الگوی غیرمجاز، تسویه ناسازگار، اطلاعات خریدار ناقص، شناسه کالا یا واحد تأییدنشده، تاریخ خارج از بازه و JSON دارای فیلد ممنوع اضافه می‌شوند.
- قبل از ادعای آمادگی ارسال، build و آزمون‌های دامنه، API، projection، امضا، outbox، dispatch و reconciliation اجرا می‌شوند. برای هر محیط، یک ارسال واقعی کنترل‌شده و رسید/استعلام همان فاکتور جداگانه تأیید می‌شود.

## منبع و قواعد تأییدشده

فایل کاربر `RC_IITP_IS_V7_9_2.pdf` باز شد و SHA-256 آن با آرشیو `TAX-ISSUE-79` در `docs/references/tax-authority-sdk-catalog.md` برابر است: `fb333770cddafd92d4ed3a5db0a21c1b0c47305431598f297f70fe5dd4c416be`.

- صفحه ۱۴، جدول ۱: نوع ۲ با الگوی فروش ۱ مجاز است؛ اطلاعات خریدار اختیاری است. فیلدهای `setm`، `cap` و `insp` برای ترکیب نوع ۲/الگوی فروش خارج از الگو (`ignore`) هستند.
- صفحه ۲۸، جدول ۶: اطلاعات خریدار برای نوع ۲ الزامی نیست و کل مبلغ صورتحساب نقدی تلقی می‌شود.
- صفحه ۲۹، جدول ۹: الگوی فروش ۱ یکی از الگوهای نوع ۲ است.
- صفحه ۴۵، جدول ۲۴: نوع تسویه برای نوع ۲ نقدی است.
- صفحه ۹۷ فقط schema عمومی JSON را نشان می‌دهد، نه یک نمونهٔ JSON کامل و مقداردهی‌شدهٔ نوع ۲؛ بنابراین آزمون‌ها باید به قواعد/فیلدهای مستند تکیه کنند و خروجی ساختگی را نمونهٔ رسمی ننامند.

## تصمیم اجرایی نهایی

- نوع ۲ فقط برای صورتحساب اصلی با `inty=2`, `inp=1` فعال می‌شود؛ الگوها و موضوع‌های دیگر نوع ۲ بسته می‌مانند.
- در UI نوع ۲ اطلاعات خریدار و کنترل تسویه حذف می‌شوند. سرور نیز خریدار را لازم نمی‌داند و مقادیر خریدار/تسویهٔ باقی‌مانده در draft را رد یا از payload حذف می‌کند.
- در payload نوع ۲، اطلاعات خریدار، `setm`، `cap` و `insp` ارسال نمی‌شوند. مبلغ کل با قاعدهٔ «تمام مبلغ نقدی تلقی می‌شود» نگهداری می‌شود.
- مسیر فعلی امضا/ارسال Sandbox و Production و reservationهای محیطی استفاده می‌شوند؛ تنها projector نوع ۲/فروش اصلی به آن‌ها افزوده می‌شود. هیچ fallback بین environmentها مجاز نیست.
- پشتیبانی کد به معنی ارسال خودکار نیست. کاربر برای هر صورتحساب و محیط همان عملیات ارسال صریح و موجود را انجام می‌دهد؛ هیچ ارسال واقعی در تست‌ها انجام نمی‌شود.

## پیش‌نیازهای اجرای زنده

- برای هر محیط، حافظهٔ تأییدشده و کلید/credential موجود باید همان محدودیت‌ها و گیت‌های فعلی را پاس کنند.
- این تغییر مسیر کد را برای Type2/1 باز می‌کند، اما وضعیت Production deployment یا فعال‌سازی سرویس‌ها را تغییر نمی‌دهد. ارسال واقعی بعد از deploy نیازمند مجاز بودن سرویس و انتخاب صریح یک فاکتور است.

## خارج از محدوده

- ارسال خودکار/زمان‌بندی‌شده یا ارسال بدون تأیید همان فاکتور و محیط.
- فعال‌سازی سرویس‌ها، تغییر secret یا کلید، اجرای migration، تغییر پایگاه دادهٔ عملیاتی؛ این‌ها نیازمند اجرای runbook و تأییدهای موجود خودشان هستند.
- فعال‌کردن الگوهای تخصصی، نوع سوم، اصلاح/ابطال/برگشت نوع ۲ یا قرارداد نوع ۲.
